## REG: причина остановки теперь установлена точно

Добавлена только собственная проверка `.github/workflows/osminog-reg-preflight.yml` в OSMINOG, environment `osminog-reg`. Исходный commit **9ed19c94e03d4a71e19ea5d8a201513b0ec559b9**. [Run 42381669273](https://github.com/jeep-jim/OSMINOG/actions/runs/42381669273), job **128430404336** остановился на `Require OSMINOG-owned configuration` с явным сообщением:

`OSMINOG_REG_SSH_KEY is not available to this OSMINOG workflow.`

В прочитанном журнале переменные SSH_PRIVATE_KEY и SSH_USER пустые; шаг SSH пропущен. Это означает отсутствие доступного отдельного секрета у этой проверки, а не поломку REG, отсутствие памяти или падение другого приложения. На сервер в этой сессии подключения не было, ничего там не менялось. Защиты окружения не обходились.

Workflow также помещён в main как собственная read-only проверка с workflow_dispatch, чтобы после легитимной настройки доступа её можно было запускать из OSMINOG. Включение файла не создаёт ключ/пользователя и не является деплоем. Ничего не устанавливается; root и чужие аккаунты отклоняются. Проверка использует закреплённую публичную идентичность SSH-хоста, не ослабляет её.

Для следующего этапа администратор должен однократно подготовить на разрешённой REG VM отдельный непривилегированный аккаунт `osminog`/`osminog-deploy` и новый ключ только для него. Приватную часть вводить непосредственно в **OSMINOG → Settings → Environments → osminog-reg → Environment secrets → OSMINOG_REG_SSH_KEY**, не отправлять в переписку или исходники. Для нестандартного имени аккаунта — variable OSMINOG_REG_SSH_USER. Не копировать ключ АвтоЦены и не добавлять пользователя в sudo/docker группы. Сначала read-only проверка, затем отдельно ограниченное управление только сервисом OSMINOG. В ветке имеется инструкция `infra/intent-ocean/CONNECT-REG.md`.
