## Диагностический эксперимент

Отдельный push workflow собирает пакет приложения с тем же production-кодом
859 и диагностическими smoke hooks. Он не создаёт DMG/ZIP релиза, не заполняет
pins, не запускает publisher и не заменяет полный native acceptance.

Существующий `--mouse-631-smoke` запускается последовательно в двух отдельных
процессах: без CPU profiling и с явным opt-in. Каждый получает новый cwd и
абсолютный временный профиль. Обе исходные стадии20/50 страниц, все15
переключений, HTTP streams, проверки пикселей и identities, период опроса и
таймауты workload сохраняются. Дополнительного прогрева нет. Исходные
верификационные файлы и неудавшиеся попытки не перезаписываются.

Для opt-in записываются CPU profiles основного процесса и shell renderer,
ограниченные метки существующих switch/settled IPC и исходные отметки времени.
Clock domains сохраняются отдельно. CPU sampling может влиять на время;
его результаты предназначены для атрибуции работы, а не замены релизных
измерений. По двум CPU profiles нельзя обещать точную одностороннюю IPC latency.

Python runner сохраняет реальные PID, exitCode, timeout, маркеры и SHA-256
сырых файлов. При таймауте завершается только созданная им группа процесса.
Профили не включаются в ограниченный8MiB stress report. Manifest явно содержит
`diagnosticOnly=true` и `releaseAcceptance=false`, даже если сбор данных успешен.

Указанные владельцем графические зависания36 при переходе в обычный вид
требуют отдельной проверки в опубликованной37. Этот эксперимент не доказывает
их причину или устранение. Исходное требование и снимок сохранены в основном
журнале37; повторно адреса репозиториев у владельца не запрашиваются.
